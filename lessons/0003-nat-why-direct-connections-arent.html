NAT：为什么互联网上的「直接连接」不直接

第 3 课 · P2P 最硬核的部分 —— 你点名的盲区。本课回答：为什么两台设备在局域网秒连，搬到互联网就废了。

🎯 本课实得收获：上完这课，你能解释「为什么你的 app 在局域网不需要 STUN/TURN，而跨网就必须」——并说出 NAT 四种行为的精确区别（全锥 / 限制锥 / 端口限制锥 / 对称）。

一个你早就知道的现象

你的 LocalTransfer 在 iPhone ↔ iPad ↔ Mac 之间秒连——因为它们在同一个局域网，设备互相直接可达。但想象把两台设备放到两个不同的家庭 WiFi 后面：A 想给 B 发一个 UDP 包，B 收不到。为什么？

因为中间隔着路由器，而路由器上跑着一个叫 NAT（Network Address Translation，RFC 2663）的东西。

为什么会有 NAT

两个历史原因：

  • IPv4 地址不够分：全世界只有约 43 亿个 IPv4 地址。解决办法是：内网设备用私网地址（10.x / 172.16–31.x / 192.168.x，RFC 1918），只有路由器占一个公网地址，NAT 负责翻译。
  • 默认安全：NAT 顺带成了防火墙——内网设备可以出去，但外面的人默认进不来。

NAT 的机制：一张映射表

NAT 的核心是一张「映射表」：

内网端点 (private)        ↕      公网端点 (public)
192.168.1.5:54321        ↔      203.0.113.7:62000
192.168.1.8:32100        ↔      203.0.113.7:62001
  • 出站：内网设备发一个包 → NAT 在表里建一条映射（如果还没有）→ 改写源地址为公网端点 → 发出去。
  • 入站：外面来了一个包 → NAT 查表，目的公网端点有映射 → 改写成内网端点转发进去；没有映射 → 直接丢弃。
核心矛盾

P2P 的本质需求是「别人能找到我」；NAT 的默认策略是「别人找不到我」。整个 NAT 穿越（traversal）领域，都是在跟这个默认策略周旋。

四种 NAT（RFC 3489 §5 的权威分类）

不同 NAT 的行为不一样。RFC 3489 观察到四种行为，用两个维度区分：映射行为（同一内网端点对外是固定一个公网端点，还是每目的地一个）和过滤行为（谁可以给我发入站包）。

类型映射过滤（谁能进）
全锥
full cone		固定（同一内网端点 → 同一公网端点）任意外网主机
限制锥
restricted cone		固定仅「我曾发过包给它的 IP」
端口限制锥
port restricted cone		固定仅「我曾发过包给它的 IP:端口」
对称
symmetric		每目的地一个（同一内网端点发给不同目的地 → 不同公网端点）仅收到过我包的对方

RFC 3489 对四种类型的原文定义：

Full cone: all requests from the same internal IP address and port are mapped to the same external IP address and port. Furthermore, any external host can send a packet to the internal host, by sending a packet to the mapped external address. … Symmetric: all requests from the same internal IP address and port, to a specific destination IP address and port, are mapped to the same external IP address and port. If the same host sends a packet … to a different destination, a different mapping is used.

—— RFC 3489 §5 NAT Variations

关键洞见

STUN 能告诉你「我在 NAT 外面的地址」——但这个地址只有在映射行为是「固定」时才对别人有用。对称 NAT 下，STUN 服务器看到的映射是「发给 STUN 服务器」这个目的地专用的；你的对端往那个地址发包，NAT 会开一条新的映射而不是复用旧的，包根本到不了你。RFC 3489 的适用性声明直接说了：「STUN does not enable incoming UDP packets through symmetric NATs」。

映射还会过期

UDP 没有连接状态，NAT 无法知道会话何时结束，只能靠空闲计时器回收映射。Ford 等人的经典论文测过：有的 NAT 空闲 20 秒就关洞。所以 P2P 连接建立后必须周期性地发 keepalive，否则洞会消失（Ford, Srisuresh & Kegel, USENIX 2005）。ICE 里对应的是「consent freshness」机制：连接后每隔几秒重探一次，若 30 秒内没有应答，必须停止发送（RFC 7675）。

对号入座：你的 LocalTransfer

  • 为什么局域网不需要 STUN/TURN：同一网段内，两台设备的 192.168.x.x 地址互相本来就能直达——没有 NAT 横在中间，host 候选者直接可用。这就是你 iceServers: [] 的全部合理性（CONTEXT 约束「v1 无跨网需求」）。
  • 为什么「路由器 AP 隔离 / 跨 VLAN」是你列的关键风险：AP 隔离是路由器主动过滤同网段设备间的流量——本质就是「过滤行为」的另一种形态。一旦开启，你的 host 候选者之间的包被丢弃，连接失败。
  • 未来跨网怎么做：加上 STUN → 获得 server-reflexive 候选（typ srflx）；加 TURN → 获得 relayed 候选（typ relay）。这正是第 4 课的内容。

测验

Q1. 外部主机主动发来的入站包，NAT 默认怎么处理？

  1. 无映射记录就丢弃入站
  2. 无条件转发所有入站包
  3. 建立新映射后转发进去

Q2. 为什么对称 NAT 下，STUN 获得的公网地址无法用于直连？

  1. 因为映射只对单一目的地有效
  2. 因为映射随会话一结束就失效
  3. 因为所报公网地址会定期更换

Q3. 「仅联系过的地址能发入站包」描述的是哪种 NAT？

  1. 外网任意主机都能发入站包
  2. 仅联系过的地址能发入站包
  3. 仅内网相同网段能发入站包

Q4. 为什么 P2P 连接建立后还要持续发 keepalive？

  1. 映射会因空闲超时而过期
  2. 映射会因协商失败而重建
  3. 映射会因负载过高而更换
