ICE：候选者、连通性检查与「选路」

第 4 课 · 上一课你看到了 a=candidate … typ host；本课讲完整故事：ICE 如何把「能找到我的所有地址」列出来，逐个试，选出能用的那条路。

🎯 本课实得收获：上完这课，你能解释四种候选者（host / srflx / prflx / relay）从哪来、连通性检查怎么证明一条路可用、为什么需要「控制方」单一决策——并说清你的项目当前只走 ICE 的第一步。

ICE 是什么

第 3 课我们知道了 NAT 让「你以为的地址」常常不可达。ICE（Interactive Connectivity Establishment，RFC 8445）的应对哲学是：不知道哪条路通，就把所有可能的路都列出来，逐一实测。

RFC 8445 的概述（§2）说得很直白：

Each agent has a variety of candidate transport addresses … it could use to communicate with the other agent. … The purpose of ICE is to discover which pairs of addresses will work. The way that ICE does this is to systematically try all possible pairs (in a carefully sorted order) until it finds one or more that work.

—— RFC 8445 §2 Overview of ICE

ICE 分四步：收集候选 → 交换候选（走信令）→ 配对 + 连通性检查 → 提名定选。第 1、2 步你在第 2 课已经见过（SDP 里的 a=candidate 行就是「交换」的载体）。

四种候选者（RFC 8445 §5.1.1）

类型从哪来含义
host
主机候选		本机网卡局域网地址（192.168.x.x）。只有同网段的对端能到达——你的项目唯一类型。
srflx
服务器反射		问 STUN「我外面是什么」NAT 分配的公网映射。NAT 行为正常（非对称）时外部可达。
relay
中继候选		向 TURN 申请服务器上的地址，数据经 TURN 转发。几乎总可用，代价是带宽与延迟。
prflx
对端反射		检查过程中意外发现双方都没预料到的 NAT 映射——symmetric NAT 场景下的救星（第 3 课伏笔）。

注意 base（基线地址）的概念：srflx / relay 是从「别处」映射来的地址，主机不能直接从这个地址发包——所有包都从 base（对应的 host 地址或到 TURN 的本地端点）发出。RFC 8445 明确说「an ICE agent cannot send requests directly from a reflexive candidate … but only from its base」。

优先级：先试哪条路

候选者按优先级排序，类型偏好是主导因素（RFC 8445 §5.1.2.2）：host 最高 → srflx → prflx → relay（通常为 0，最后手段）。RFC 还强制「peer-reflexive 的类型偏好必须高于 server-reflexive」。推荐公式是 priority = 2²⁴×type + 2⁸×local + component——类型权重占了 24 位，所以类型几乎总是压过同类型内的差异。

交换后，每端把自己的每个候选 × 对方的每个候选配对成候选对，按 pair priority = 2³²×MIN(G,D) + 2×MAX(G,D) + (G>D?1:0) 排序（G、D 是双方的候选优先级）。排在前面的对先试。

连通性检查：怎么证明一条路「通」

每对候选都要实测：从本地候选的 base 向远端候选发一个 STUN Binding Request（RFC 8445 §7）。收到回包意味着三件事同时成立：

  1. 这条路双向通——包能出去，回包能回来；
  2. 对方持有会话凭据——请求里带着从信令拿到的 ufrag/pwd（第 2 课那两行的用途兑现了），伪造的包无法假装成一次成功的检查；
  3. NAT 的洞已经被「双向各发一次」打开（打洞的机制性收益）。

检查按优先级顺序逐个来，节奏由计时器 Ta 控制（默认 50ms 间隔，RFC 8445 §14），并且对候选对总数有上限（默认 100 对）——这是为了防止 ICE 被利用做流量放大攻击（RFC 8445 §19.5.1）。

关键洞见

连通性检查同时完成两件事：探路 + 打洞。它本身就是「双方同时向对方公网地址发包」——正是 Ford 论文里打洞的过程。ICE 把打洞从「应用技巧」变成了「协议内建步骤」。这是理解整个 P2P 建连最关键的一步。

控制方与被控方：为什么只能一个人拍板

双方都在跑检查，但只有一方能决定用哪对。发起方默认是 controlling（控制方），另一方是 controlled（被控方，RFC 8445 §6.1.1）。控制方对选中的候选对发出带 USE-CANDIDATE 标记的检查，被控方确认后这条路被「提名」，ICE 收尾。

为什么需要单一决策者？RFC 8445 的设计动机（附录 B.7）说得清楚：如果两边各自定夺，可能各选一条不同的路，媒体数据会沿着两条路径流，连接直接错乱。所以角色必须分派，冲突时用「ice-controlling/ice-controlled」属性解决。

Trickle vs 非 Trickle：两种交换节奏

第 2 课讲过你的实现是非 trickle（等 gathering complete 一次性发完整 SDP）。浏览器默认走的是 trickle ICE（RFC 8838）：每个候选一出现就立刻经信令发过去，icecandidate 事件每触发一次发一条。host 候选几乎瞬时可用，所以在友好网络下连接可以在收集完成前就建立。

两种节奏各有理由：trickle 快，但要求信令通道支持多次小消息（你的 QR 一次只能装一个码，天然不适合）；非 trickle 慢一点，但一次搞定、适合单次装载。你的选择不是缺陷，是载体约束下的正确设计。

对号入座：你的代码在 ICE 里的位置

// src/webrtc/peer.ts
export function defaultPcFactory(): RTCPeerConnection {
  return new RTCPeerConnection({ iceServers: [] })   // ← 没有 STUN/TURN
}
  • 你只走 ICE 的第一步：收集 host 候选（网卡地址）→ 交换 → 配对 → 连通性检查。因为局域网内 host 候选直接可达，检查必过，连接秒建。
  • 加上 iceServers: [{ urls: 'stun:…' }]，SDP 里就会出现 typ srflx；加上 TURN 会有 typ relay。同一套代码，ICE 会自动处理更多候选——这是把 LocalTransfer 扩展到跨网的最小改动路径。
  • 想亲眼看检查过程：Chrome 的 chrome://webrtc-internals 能看到收集到的候选、每一对检查与最终选中的对；Firefox 是 about:webrtc。

测验

Q1. 哪种候选者是由 STUN 服务器获得的？

  1. 服务器反射候选者
  2. 主机网卡地址候选
  3. 中继转发的候选者

Q2. 连通性检查具体发的是什么？

  1. STUN 的绑定请求
  2. SDP 格式会话描述
  3. ICE 提名确认消息

Q3. 最终用哪对候选，由谁决定？

  1. 控制方提名定选
  2. 被控方等待选择
  3. 双方各自选路径

Q4. 你的项目里为什么只有 host 候选者？

  1. 未配置任何穿透服务器
  2. 局域网内无需地址映射
  3. 因为候选收集尚在进行
