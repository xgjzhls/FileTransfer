DataChannel 数据面：你的字节怎么流过去

第 7 课 · 收尾课。连接建好后，文件字节在 SCTP 上的完整旅程：ordered/reliable 语义、分块与消息上限、背压 —— 全程对照 src/transfer/sender.ts 和 SPEC §3.1。

🎯 本课实得收获：上完这课，你能讲清 DataChannel 的可靠性语义从哪来、为什么必须分块、你的 8MiB 背压阈值在防什么——并把 7 课知识串成一条完整的「点击发送 → 文件落地」链路。

你的字节站在哪一层

第 2 课的协议栈练习已经埋好答案，现在补全细节（RFC 8831 §5）：

┌─────────────────────────────┐
│ 你的应用帧（framing.ts）      │  ← 文件 id / part / chunk / 校验
├─────────────────────────────┤
│ DataChannel + DCEP          │  ← 通道语义（ordered/reliable）在此协商
├─────────────────────────────┤
│ SCTP（RFC 4960 + PR-SCTP）   │  ← 有序性、可靠性、分片重组、拥塞控制
├─────────────────────────────┤
│ DTLS                        │  ← 加密、完整性、源认证
├─────────────────────────────┤
│ ICE/UDP（RFC 8445）          │  ← NAT 穿越（第 3–6 课全部内容）
└─────────────────────────────┘

SCTP 是这份栈的引擎：多流、有序/乱序投递、可靠/部分可靠、任意大消息的分片重组、PMTU 发现、拥塞控制全部由它提供（RFC 8831 §5）。DataChannel 只是它上面一层薄薄的映射。

ordered / reliable 到底指什么

RFC 8831 明确了两个正交的维度，且都是消息级属性（不是通道级）：

维度含义实现机制
有序
ordered		按发送顺序投递SCTP 流内序号（SSN），有序消息按序上抛
可靠
reliable		丢包必重传SCTP 确认与重传（T3 计时器）
部分可靠
partial reliable		可限制重传次数 / 存活时间PR-SCTP（RFC 3758）+ 受限重传策略（RFC 7496）

DCEP 的 DATA_CHANNEL_OPEN 消息（RFC 8832 §5.1）用一个字节的 Channel Type 字段把组合编码出来——第 2 课「ordered 不进 SDP」的完整兑现：

Channel Type（1 字节）:
  0x00  DATA_CHANNEL_RELIABLE                 可靠 + 有序
  0x80  DATA_CHANNEL_RELIABLE_UNORDERED       可靠 + 乱序（最高位=unordered 标志）
  0x01  DATA_CHANNEL_PARTIAL_RELIABLE_REXMIT  部分可靠（限重传次数）+ 有序
  0x81  同上 + 乱序
  0x02  DATA_CHANNEL_PARTIAL_RELIABLE_TIMED   部分可靠（限存活毫秒）+ 有序
  0x82  同上 + 乱序

后续字段: Priority(2B) + Reliability Parameter(4B, 次数或毫秒) + Label/Protocol

你的 createDataChannel('lt', { ordered: true }) → 通道类型 0x00（可靠有序）。对文件传输这是正确选择：字节错序/丢失会让整个文件损坏。RFC 8831 用例表里「non-real-time file transfers」（U-C 4）正是这种通道的标准用例。

关键洞见

为什么 DataChannel 能「重传」——而它的底层 UDP 不能？因为 SCTP 在自己的层实现了可靠传输（确认 + 重传 + 流控），就像 TCP 之于 IP。DataChannel = 跑在 UDP 上的「类 TCP」服务，外加多流与消息边界。这是整个数据面语义的来源。

为什么必须分块：三个原因

  1. 消息上限：单条 SCTP 用户消息不能超过对方声明的 max-message-size（第 2 课：缺省 64K、浏览器协商 256KiB）。你的 CHUNK_SIZE = 256*1024 - 64 正好卡在上限内，64 字节留给帧头。
  2. 避免独占关联：没有消息交错（RFC 8260）时，一个大消息会垄断 SCTP 关联——RFC 8831 建议此时上限 16KB。现代浏览器支持交错，所以 256KiB 可用；但你的 dc.send() 每次一帧，天然不独占。
  3. 断点续传：分块让 64MiB bitfield 粒度（ADR-0005）成为可能——崩溃后只重传缺失块，不重发整个文件。

每条 SCTP 用户消息还携带 PPID（Payload Protocol Identifier）标明类型：50=DCEP、51=字符串、53=二进制（你的文件帧）、56/57=空消息。接收端靠它区分「控制消息」和「用户数据」。

背压：你已经在做的流控

发送太快会怎样？dc.send() 把帧放进 SCTP 发送缓冲区（浏览器实现），你只管调 API——如果对方接收慢或链路拥塞，缓冲区会无限涨，内存被吃掉。防这个的机制是 背压：先看积压，再决定是否继续发。

你的 src/transfer/sender.ts 是教科书实现：

export const BACKPRESSURE_LIMIT = 8 * 1024 * 1024   // SPEC §3.1: >8MiB 暂停

private async pump(frame: Uint8Array): Promise<void> {
  this.transport.send(frame)
  while (this.transport.bufferedAmount > BACKPRESSURE_LIMIT) {
    await waitForLow(this.transport)   // bufferedamountlow 事件唤醒
  }
}

机制对照（MDN）：

  • bufferedAmount = 「已排队但尚未发出」的字节数（MDN 原文：the number of bytes of data currently queued to be sent … but have not yet been sent）。
  • 你每发一帧就检查：超过 8MiB 暂停；浏览器在积压降到 bufferedAmountLowThreshold（peer.ts 里设成阈值一半 = 4MiB）时触发 bufferedamountlow 事件唤醒发送循环。
  • 结果：在途数据始终 ≤ 8MiB，内存有界；发送速率自动贴合接收方处理能力——这就是「窗口式流控」在浏览器层的实现。

为什么是 8MiB？太小→吞吐受往返延迟限制（发送方经常空等）；太大→崩溃时丢的数据多（8MiB 在途 × 重传成本）。你的选择是吞吐与风险的折中——也正好是「传输帧 256KiB、bitfield 粒度 64MiB」粒度体系里的一环。

关闭通道与 SCTP 流重置

DataChannel 关闭不是「发一条再见」：关闭方重置对应的 SCTP 流（RFC 6525），对端看到流被重置后也重置自己的出站流，双方完成后通道才真正关闭——重置保证「已发消息要么送达要么放弃」之后才释放流（RFC 8831 §6.7）。你的 RtcPeer.close() 调 dc.close() 时，浏览器在幕后做的就是这件事。

收尾：把 7 课串成一条链路

现在你能完整讲出「点击发送 → 文件落地」的每一层了：

  1. 信令（第 1 课）：WS/QR 双载体交换 SDP offer/answer——为什么必须双向、为什么离线两跳。
  2. SDP（第 2 课）：m=application … UDP/DTLS/SCTP webrtc-datachannel + ICE 凭据 + max-message-size。
  3. NAT（第 3 课）：为什么跨网需要穿透；局域网 host 候选直达。
  4. ICE（第 4 课）：收集→交换→连通性检查→提名；你的栈只有 host。
  5. 打洞（第 5 课）：检查即打洞；对称 NAT 失败、prflx 救场。
  6. TURN（第 6 课）：打洞失败的兜底与成本。
  7. 数据面（本课）：DTLS 加密 → SCTP 有序可靠投递 → DCEP 建通道 → 你的 256KiB 帧 → 8MiB 背压 → OPFS 落盘。

测验

Q1. createDataChannel 的 ordered 参数在 DCEP 里怎么传递？

  1. 写在通道类型字节的最高位
  2. 写在会话描述的媒体属性行
  3. 写在候选者网络地址字段内

Q2. 部分可靠（partial reliable）通道可以怎么约束？

  1. 限制重传次数或存活时间
  2. 限制通道数量或消息大小
  3. 限制连接时长或加密强度

Q3. 你的背压机制靠什么判断要不要暂停发送？

  1. 检查待发送的字节数暂停发送
  2. 检查连接状态失败后重连通道
  3. 检查磁盘配额不足则清理空间

Q4. 每条 SCTP 用户消息携带的 PPID 有什么作用？

  1. 每条消息携带类型标识字段
  2. 每条消息带通道号标明序号
  3. 每条消息带端口号标明流向
