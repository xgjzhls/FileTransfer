SDP 里到底写了什么

第 2 课 · 把二维码里那段 gzip 文本解压出来，逐行读懂 —— 全程对照你自己的代码。

🎯 本课实得收获：上完这课，你能指着任意一段 SDP 说出每行在干什么，并且明白三个「原来如此」：max-message-size 就是你 256KiB 帧的出处、ordered:true 根本不在 SDP 里、iceServers: [] 意味着你的 SDP 里只有 host 候选者。

起点：你的 SDP 管线

先看 src/webrtc/peer.ts 里 offer 是怎么诞生的 —— 整条链其实只有 6 行关键代码：

async createOffer(): Promise<string> {
  const dc = this.pc.createDataChannel('lt', { ordered: true })  // ① 建通道
  const offer = await this.pc.createOffer()                        // ② 生成 offer
  await this.pc.setLocalDescription(offer)                         // ③ 设为本地描述
  await waitForGatheringComplete(this.pc)                          // ④ 等候选收齐
  return compressSdp(this.pc.localDescription!.sdp)                // ⑤ 压缩后返回
}

两个值得停下的细节：

  • ④ 是非 trickle（一次性）信令：你的实现必须等 iceGatheringState === 'complete' 才取 localDescription.sdp——否则 SDP 里还没有候选者。对比第 1 课讲的 MDN 流程（一边收集一边发 candidate），你为了配合「扫码只能传一次」的场景，把候选者全部内联进了一份 SDP。这是单载体（QR）对协议的约束，不是偷懒。
  • ⑤ 压缩：看 src/webrtc/sdpCodec.ts，就是 gzip + base64url。SDP 是高度重复的文本，gzip 能压掉 90%+——你的注释里写「候选密集的 offer 可压 90%+」。为什么这么有效，马上就看到。

SDP 是什么：一行一行的文本

SDP（Session Description Protocol，RFC 8866）是纯文本、行式、key=value 的协议。每行一个字段，v=、a=、m= 这种前缀是字段名。结构分两级：

  • 会话级（文件开头）：v=、o=、s=、t=，加上作用于整个会话的 a= 属性
  • 媒体级（每个 m= 行开始的一个块）：描述一条媒体流或数据通道，块内的 a= 只作用于它

这就是为什么 gzip 效果拔群：每行都有固定前缀、重复的模板结构，压缩器最爱的输入。

逐块看：

会话级：v= / o= / s= / t=

RFC 8866 的固定开场。对连接本身几乎没用（o= 的 id 用于区分会话版本，重协商时会变）。读到这里可以跳过。

a=ice-ufrag / a=ice-pwd —— 打洞的「钥匙」

这两行是 ICE 凭据（RFC 8445）。两台设备要通过 NAT 打洞互相发包时，收到的包必须带着正确的 ufrag/pwd 才被认作「自己人」。每端随机生成自己的，只在 SDP 里交换给对端。第 4 课会展开——现在先知道：它们让对端能校验「收到的包确实来自协商好的对端」。

a=fingerprint / a=setup —— 加密层（DTLS）

你的文件字节在传输前会被 DTLS（UDP 上的 TLS）加密。a=fingerprint 是本端自签证书的指纹，对端用它验证握手对象没被中间人替换；a=setup:actpass 声明「DTLS 角色我两种都行」，answer 端必须挑一个（active 或 passive），避免两端都等对方先开口（RFC 8841 §9.4）。

★ m=application 9 UDP/DTLS/SCTP webrtc-datachannel —— 最重要的一行

格式是 m=<类型> <端口> <协议> <格式>（RFC 8841 §4）：

字段你的值含义
类型application不是音视频，是应用数据
端口9占位符——真实端口由下面 a=candidate 给出
协议UDP/DTLS/SCTP整条协议栈：UDP 承载 DTLS，DTLS 承载 SCTP
格式webrtc-datachannel这条 SCTP 关联的用途 = WebRTC 数据通道（RFC 8832/8841 注册名）

★ a=max-message-size:262144 —— 你 256KiB 帧的出处

RFC 8841 §6：SCTP 用户消息（即 DataChannel 上一条 send() 的内容）有大小上限；缺省是 64K，且绝不能超过对方声明的值。现代浏览器协商到 262144（256KiB）——MDN 说「most modern browsers support sending messages of at least 256 kilobytes」。你的 SPEC 把它记为硬上限，chunk = 256KiB − 64，那 64 字节是留给帧头的。现在你知道这数字是从哪冒出来的了。

★ a=candidate … typ host —— 你的地址清单

每个候选者 = 「你可以这样找到我」。局域网 + iceServers: [] 意味着只有 host 类型：网卡上的真实地址（192.168.x.x / 10.x.x.x）。这就是为什么你的两个设备必须同一网段——候选者清单里只有局域网点。第 3/4 课讲 NAT 后你会看到加一个 STUN 会多出 typ srflx（公网映射地址）。

关键洞见

你在 createDataChannel('lt', { ordered: true }) 里设的 ordered，根本不会出现在 SDP 里。通道参数（ordered/reliable/label）走的是 DCEP（RFC 8832）——SCTP 关联建立后，在带内发一条「打开通道」的控制消息来协商。SDP 只负责「把 SCTP 关联建起来」，通道本身是建好之后的事。

answer 与 offer 的关系

对照 RFC 8841 §13.1 的真实 offer/answer 对（上节课你已经知道 answer 必须基于 offer 生成），注意三个呼应：

  • m= 行的 协议字段必须与 offer 一致（answer 写 UDP/DTLS/SCTP），但端口各自报各自的
  • a=setup：offer 写 actpass，answer 必须收敛成 active 或 passive —— 不然两端都等对方先握手
  • a=sctp-port 双方各选各的端口；a=max-message-size 双方各报各的接收上限（可能不同）

你的 acceptAnswer() 把解压后的 answer 直接 setRemoteDescription 完事——因为 answer 里没有新东西需要协商，ICE 层拿到双方候选者后自己开始连通性检查，连上即 connected。

三个「对号入座」

  1. max-message-size 262144 ↔ 你的 256KiB−64 帧：不是拍脑袋定的，是浏览器协商出的单条消息上限。
  2. ordered:true ↔ 不在 SDP 里：通道参数走 DCEP 带内协商（RFC 8832），SDP 只建 SCTP 关联。
  3. iceServers: [] ↔ 只有 typ host 候选者：局域网 P2P 的全部地址清单就是两张网卡——这也预告了下一课：为什么一旦跨网，事情就变复杂。

测验

Q1. m=application 9 UDP/DTLS/SCTP webrtc-datachannel 中的 UDP/DTLS/SCTP 表示什么？

  1. 数据通道的完整协议栈
  2. 数据通道的应用层协议
  3. 数据通道的加密算法套件

Q2. 为什么你的 offer 里只有 host 类型候选者？

  1. 因为未配置任何穿透服务器
  2. 因为局域网内无需地址映射
  3. 因为候选者收集还在进行

Q3. a=max-message-size:262144 直接对应你 SPEC 里的什么？

  1. 单条消息大小的上限
  2. 单个文件大小的上限
  3. 单条 SDP 长度的上限

Q4. createDataChannel('lt', { ordered: true }) 里的 ordered 会写进 SDP 吗？

  1. 不会，通道参数走带内协商
  2. 会的，写入 a=ordered 属性
  3. 会写入媒体行的属性字段
