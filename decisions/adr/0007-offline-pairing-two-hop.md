# ADR-0007: 离线配对保持「两跳」——拒绝一扫码旁路

- 状态：已接受（2026-08-15 用户确认）
- 日期：2026-08-15
- 来源：grill-with-docs 访谈（2026-08-15）

## 背景

- **用户实际主场景是完全离线**（无互联网）：离线扫码配对不是「兜底」而是常态。两跳（手机扫电脑的 offer 码 → 电脑扫/粘手机的 answer 回码）是每次使用的必经流程，来回两趟是主要摩擦点
- **诉求**：「手机扫一遍直接配对」，不要来回两趟
- **技术事实**（本访谈核实）：离线 + 纯浏览器下 WebRTC 必须双向交换 SDP，二维码是单向通道，且不存在第二条回传通道——浏览器无法监听端口（无局域网中继）、无法发裸 UDP、无跨设备剪贴板；「电脑端不做桌面应用」「零安装」约束排除了桌面信令帮手。**一扫码离线配对物理上不可行**（在线可行，见下）
- 在线场景已有零扫码路径（对称 PIN 房间，ADR-0006）；「一码自动直连」（QR 携带 room+deviceId，扫码即连）技术可行，但用户主场景离线，优先级低

## 考虑过的选项（均被拒，记录以阻止未来重提）

1. **桌面信令帮手**（打破「电脑端不做桌面应用」约束；二维码携带 `http://电脑IP:端口/pair`，手机扫码后自动 POST 回码）：可靠、真一扫码。但①违背「零安装/统一网页」核心定位；②每台电脑需安装维护；③手机↔手机离线仍两跳（手机不能监听端口，帮手帮不上）——拿核心定位换边缘便利，不值得
2. **音频配对**（纯浏览器：手机放音、电脑麦克风听音解码，Google Tone 原理）：不打破约束，但回码约 700 字节需编码成 10–30s+ 声波、环境噪声敏感、电脑需麦克风（与「无摄像头」痛点同源），只适合备选

## 决策

1. **接受离线两跳为物理上限**，保持全部既定约束（零安装、无桌面应用、无局域网中继、电脑不必在场）；第二跳以「电脑扫码」或「粘贴文本」完成（按设备能力）
2. **目标体验 = 扫码后自动直连、零点击**（延续 ADR-0006 安全模型：物理在场即信任）：在线路径若实现一码配对（QR 携带 room+deviceId → 扫码自动建连），按此体验设计；**本次不落地**（主场景离线）
3. **本次打磨范围 = 离线配对两跳体验**（条目已定，2026-08-15 访谈；SPEC §5.3）：回码全屏展示、电脑端主次按钮重排（粘贴为主操作）、回码一键分享（Web Share）、断线快捷重配入口；不做 pick 页引导折叠

## 后果

- 正面：约束零破坏；两跳体感经打磨后接近一扫码；无服务端/协议改动；数据面与传输不动
- 负面 / 边界：
  - 离线一扫码永远不可达——本 ADR 即为未来重提此事的答复（理由见「考虑过的选项」）
  - 若未来引入桌面帮手 / 音频通道，需先修改本 ADR 与相关约束
  - 手机↔手机离线配对仍两跳（无桌面帮手可依赖）
  - 待真机验证：打磨后的整体配对体验（T08 多端联调）
